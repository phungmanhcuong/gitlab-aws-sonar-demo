Shortlinks: a delivery pipeline you can teach from

One small API taken from a laptop to production the way a professional team would: every change through a merge request, a self-hosted SonarQube quality gate, scanned images promoted unchanged, and AWS deploys with no stored keys. Every number on this page was measured on the real setup on 12 Nov 2026.

0The big picture

  • The service: shortlinks, FastAPI, 167 lines of code, 12 tests.
  • GitLab.com hosts the code and runs almost every job on GitLab's own throwaway runners.
  • SonarQube Community Build runs on our own Docker host; only the Sonar job runs there.
  • AWS hosts staging and production; jobs log in with short-lived OIDC credentials.
git clone https://github.com/phungmanhcuong/gitlab-aws-sonar-demo.git && cd gitlab-aws-sonar-demo
git remote add gitlab git@gitlab.com:<your-group>/gitlab-aws-sonar-demo.git   # the pipeline runs on GitLab
make setup && make check      # uv sync, ruff, mypy, pytest (80 % floor)
make run                       # http://127.0.0.1:8080/docs

Check it curl https://<api-id>.execute-api.ap-southeast-1.amazonaws.com/health returns {"status":"ok","env":"staging","version":"<SHA of main>"}.

1Repository and conventions

  • Branches live hours to days: feature/…, fix/…, exercise/….
  • Every change is a merge request; the template asks what changed, how it was checked and how to roll back.
  • Decisions with lasting effect get a short ADR in docs/adr/.
git switch -c feature/stats-endpoint
git commit -am "Add stats endpoint"
git push -o merge_request.create -o merge_request.target=main -u origin feature/stats-endpoint

Check it the merge request shows a running pipeline within seconds; the Merge button stays disabled until it is green.

3GitLab project setup

  • Project settings: merge only with a green pipeline and resolved threads; semi-linear history; delete the source branch.
  • Protected main: push No one, merge Maintainers. Protected tags v*: create Maintainers.
  • Variables: role ARNs and the state bucket are plain; SONAR_TOKEN is masked, hidden and protected.

4Self-hosted SonarQube

  • Size: SonarQube capped at 3 GB, PostgreSQL at 512 MB; measured use 2.48 GiB SonarQube, 124 MiB PostgreSQL, 19 MiB runner. Ready about 35 s after start.
  • Its search engine needs vm.max_map_count=524288 on the host (the default was 65530).
  • The setup script replaces admin/admin with a random password and creates a project analysis token: it can analyse this one project and nothing else.
  • Every change meets the gate: sonar.qualitygate.ignoreSmallChanges=false. The default skips coverage when a change has fewer than 20 new lines to cover; exercise 01 has 18.
  • Database dump every night at 19:30 UTC, 7 days kept.
scp -r sonar desk:~/sonarqube-setup && ssh desk 'bash ~/sonarqube-setup/setup.sh'
ssh -N -L 9000:127.0.0.1:9000 desk      # then open http://localhost:9000

Check it the sonarqube job log ends with QUALITY GATE STATUS: PASSED; analysis 22 s, job 42 s.

5Runners

  • The desk runner is a project runner registered through the API; its token goes from GitLab straight into the host's config file over SSH and is never printed.
  • Jobs run with runc. gVisor (runsc) was tried and failed: Docker's embedded DNS does not reach a gVisor container on a user-defined network.
# sonar/runner/config.toml.tmpl (excerpt)
concurrent = 1
[[runners]]
  executor = "docker"
  [runners.docker]
    network_mode = "sonar-net"
    privileged = false
    allowed_images = ["python:3.13.18-slim-trixie"]
    services_limit = 0
    security_opt = ["no-new-privileges:true"]

Check it a merge request pipeline has no sonarqube job; Settings › CI/CD › Runners shows desk-sonar as protected.

6The pipeline

  • workflow:rules gives one pipeline per change: a merge request pipeline while an MR is open, otherwise a branch pipeline.
  • needs: turns stages into a graph; interruptible cancels a pipeline when a newer commit arrives.
  • Every image is pinned by version; deploys to one environment never overlap (resource_group).
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
  auto_cancel:
    on_new_commit: interruptible

Check it push twice to a branch with an open MR: one pipeline per push, and the older one is cancelled.

7AWS access without keys

  • An admin runs infra/bootstrap/bootstrap.sh once. Every policy passes IAM Access Analyzer before it is created.
  • Roles the pipeline creates (the Lambda role) must carry the boundary shortlinks-boundary: DynamoDB items and log lines, nothing else.
  • The deploy role ARNs are protected variables, so a merge request pipeline cannot read them. trust-guard builds the ARN from AWS_ACCOUNT_ID; the trust policy, not the variable, refuses the branch.
  • Access Analyzer does not list apigateway:TagResource, yet IAM requires it to create a tagged stage. The bootstrap accepts exactly that finding.
.aws:
  id_tokens:
    GITLAB_OIDC_TOKEN: { aud: https://gitlab.com }
  variables:
    AWS_WEB_IDENTITY_TOKEN_FILE: /tmp/gitlab-oidc-token
deploy-staging:
  variables: { AWS_ROLE_ARN: $ROLE_ARN_STAGING }
  script:
    - printf '%s' "$GITLAB_OIDC_TOKEN" > "$AWS_WEB_IDENTITY_TOKEN_FILE"
    - terraform apply …

Check it the trust-guard job: PASS: …-ci-staging refused fix/apigw-tag-actions (AccessDenied).

8Infrastructure as code

  • Terraform 1.17.2 with the AWS provider 6.72. Checks on every MR: fmt, validate, tflint, Trivy config.
  • The service stack looks the image tag up in ECR and pins the Lambda function to the digest.
terraform -chdir=infra/stacks/service init \
  -backend-config="bucket=$TF_STATE_BUCKET" -backend-config="key=service/staging.tfstate"
terraform -chdir=infra/stacks/service apply -var-file=envs/staging.tfvars -var "image_tag=$CI_COMMIT_SHA"

Check it first staging apply: staging 65 s after one IAM fix (stage tagging); production 70 s, 15 resources.

9Deploy, release, rollback

  • Staging: every main pipeline. Production: a v* tag on a main commit, then the manual deploy-production job.
  • A smoke test runs after each deploy: 4 must-pass and 2 must-fail requests against the real endpoint.
  • Rollback: Operate › Environments › staging › Re-deploy on an older deployment.
git tag -a v0.1.0 -m "First release" <sha on main> && git push origin v0.1.0
# pipeline: deploy-production (click ▶) → smoke-production → release

Problems met while building this, and the fix

  1. Lint and types fail on the first push. ruff E501 (2 lines over 100 characters) and mypy strict (dict is invariant: use Mapping). Expected on day one; fixed in MR !1.
  2. SAST and secret detection skipped. Template jobs wait for the previous stage; after a failed lint they were skipped. Give them needs: [] so they start at once.
  3. SAST missing from merge request pipelines. GitLab's templates run in MR pipelines only with AST_ENABLE_MR_PIPELINES: "true".
  4. Trivy checks bundle not found. public.ecr.aws/aquasecurity/trivy-checks:1 answered MANIFEST_UNKNOWN; keep the default registry for checks, use the ECR mirror only for the vulnerability DB.
  5. First image blocked: 7 HIGH CVEs. zlib1g fixed in Debian but not yet in the newest python slim digest; msgpack, setuptools and urllib3 vendored inside pip. apt-get upgrade at build time and uninstall pip.
  6. Lambda refuses the image index. Build with --provenance=false --sbom=false so the registry gets one image manifest; keep the SBOM as a separate artifact.
  7. docker compose missing on the host. Docker 25 from the distribution had no compose plugin: install v5.6.1 and verify its sha256.
  8. SonarQube setup script stopped early. Under set -e and pipefail, curl against a port that is not listening yet ends the script; add || true inside the wait loop.
  9. Elasticsearch needs vm.max_map_count. 65530 by default; set 524288 in /etc/sysctl.d before starting SonarQube.
  10. Jobs in gVisor cannot resolve DNS. Docker's embedded DNS (127.0.0.11) on a user-defined network does not reach a runsc container; the desk runner uses runc.
  11. pysonar on arm64 asks for arch=other. SonarQube answers HTTP 400 when the scanner downloads its JRE; pass -Dsonar.scanner.arch=aarch64.
  12. IAM policy over 6,144 characters. The staging CI policy was 6,343: drop read statements that the environment statements already cover (5,503).
  13. Access Analyzer and IAM disagree on API Gateway tags. Access Analyzer calls apigateway:TagResource an invalid action, but creating a tagged HTTP API stage is denied without it. Grant it and let the bootstrap accept exactly that finding.
  14. zsh ate part of a role ARN. In zsh, "$A:role" applies the :r modifier to $A and drops ":r". Use ${A} inside strings; AWS answered "Request ARN is invalid".
  15. trust-guard never ran in merge requests. Protected variables are hidden from MR pipelines, so a rule on $ROLE_ARN_STAGING was always false. Build the ARN from the account ID; ARNs are not secrets.
  16. Auto-merge silently dropped. A failed MR pipeline cancels "merge when pipeline succeeds". After fixing and re-running, merge again by hand.
  17. SonarQube skips coverage on small changes. With fewer than 20 new lines to cover, coverage and duplication conditions are ignored (31.8 % passed). Set sonar.qualitygate.ignoreSmallChanges=false.
  18. # noqa does not silence SonarQube. ruff accepted random.choice with noqa: S311; SonarQube 26.11 still raised python:S2245 as a MAJOR issue (not a hotspot), and the gate failed.
